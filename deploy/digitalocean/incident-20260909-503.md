# September 9, 2026 production 503 and staff-page stalls

Incident response began at 23:23 UTC with user authorization to restore the live
service. No database migration, data restoration, DNS change, credential change,
or full application release was performed.

## Observed failure chain

- Public HTTPS returned the load balancer's `503 No server is available` page.
  All six named web hosts were reachable with Node and NGINX running and ample
  CPU, memory and disk headroom.
- Readiness failures primarily identified `artifact_storage: false` and
  `Request aborted`. Authenticated Spaces list/head requests intermittently
  exceeded the effective two-second deadline; one list succeeded in 7.769 s.
  Both ordinary DNS routing and a diagnostic public-DNS route showed delays.
  No DNS configuration was changed. DigitalOcean's public status page did not
  identify a corresponding incident when checked; the provider-side cause is
  not established.
- SQL statement/pool timeouts occurred under traffic, but two direct database
  snapshots found no blocking sessions or long transactions. Do not present this
  as proof that database performance was healthy throughout the incident.
- Compatibility PHP-FPM had the distribution default of five children and
  repeatedly logged `pm.max_children` exhaustion. Stack-only slow logs showed
  editor requests holding PHP session locks during project-bundle HTTP requests,
  while other requests blocked in `session_start()`.

## Applied repairs

Compatibility (`144.126.222.110`), on the existing
`0406b37c54534ff9c2719f9d2bed0a0cbbcfb315` release:

- `public/measure/internal/editor.php` now closes the session immediately after
  reading it, before project/network work. This page only reads session identity;
  authentication checks and the in-memory identity remain unchanged. The same
  three-line change is preserved in the main workspace. Deployed SHA-256:
  `852f8b75cbf1698ff7630e2b5625999f5a126f2e0f70a18498cd3d4cfcd51787`.
- The source was atomically replaced, then its modification time advanced so
  PHP opcode timestamp validation loads the new code. Subsequent slow-log stacks
  reference the new line 443, confirming that the patched code executes.
- PHP-FPM `www.conf`: `pm.max_children=20`, `pm.start_servers=4`,
  `pm.min_spare_servers=4`, `pm.max_spare_servers=8`. Configuration validation
  passed before graceful reload. Observed children used about 18–56 MiB each;
  the host retained more than 2 GiB available memory. A later sample showed two
  active requests and six idle children.

Web readiness mitigation, rolled sequentially over the six known web nodes:

- `/etc/firstmeasure/incident-readiness-20260909.env` contains
  `READINESS_DEPENDENCY_TIMEOUT_MS=15000` and `READINESS_CACHE_MS=60000`.
- `/etc/systemd/system/firstmeasure-web.service.d/zzzz-incident-readiness-20260909.conf`
  loads that file with `EnvironmentFile=` last. **An initial `Environment=`
  attempt was ineffective because the older EnvironmentFiles override it.**
  Verify `/proc/<MainPID>/environ` for these two allowlisted values after restart;
  do not infer success from the drop-in text or readiness alone.
- The compatibility-host bootstrap overlay `/etc/firstmeasure/production-cutover.env`
  also contains these values for replacement nodes. Its private NGINX alias was
  checked. The autoscale template/image was not changed or replaced. This does
  not resolve the separate old-code replacement risk in 1M8-173.
- Storage/database/authentication checks remain enabled. A 60-second readiness
  cache is an incident mitigation, not a guarantee of timely application I/O.
  A durable background dependency-probe design and provider latency investigation
  remain follow-up work if delays recur.

## Validation and rollback

- PHP syntax passed. An isolated concurrent PHP session fixture retained identity
  and admitted a second reader in 0.027 s while the first request continued its
  simulated slow operation. No production session was altered by this test.
- Public portal returned its normal 302; login returned 200. Public ping, queue
  aggregates and turnaround endpoints returned successfully at several samples.
- The user's actual Chrome staff tab was first observed showing the 503 page.
  Reload reached staff sign-in; after the user signed in, the authenticated
  dashboard and populated production/QA panels were visibly verified.
- Private source rollback copy:
  `/var/cache/firstmeasure/incident-20260909/editor.php.before-session-lock`.
  Never store PHP source backups under the public web root.
- PHP pool rollback copy:
  `/etc/php/8.3/fpm/pool.d/www.conf.before-incident-20260909`.
  Validate with `php-fpm8.3 -t`, then reload gracefully if reverting.
- Bootstrap overlay backup:
  `/etc/firstmeasure/production-cutover.env.before-readiness-20260909`.
  Restore only the readiness assignments when other changes have since occurred.
- To revert web mitigation, remove only the incident drop-in/env file, reload
  systemd and roll services one at a time. Reverting reintroduces the original
  short timeout; assess current storage latency first.

The diagnostic PHP slow-log override was disabled after verification, followed
by a validated graceful reload; its stack-only incident log is mode 0600. No real project edit,
claim, test email, charge, bulk job retry or session reset was performed.

At 23:42 UTC, the first web node with verified effective settings recorded 12/12
successful readiness requests in the preceding two minutes. Staff sign-in
responded in 0.254 s. Some project requests still exceeded five seconds, so this
is recovery with latency mitigations, not proof that the storage issue vanished.
