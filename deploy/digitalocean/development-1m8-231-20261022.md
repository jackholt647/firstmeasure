# 1M8-231: "This session does not have permission" after ordering (2026-10-22)

Linear 1M8-231 (Jacob, urgent): customers ordering a report on app.1m8.ai get
"This session does not have permission to perform this action", although they
have ordering permission and the order usually goes through. Named accounts:
Hometown Roofing, Speedy Pro Roofing, Riedl and Son Exterior Specialists,
Imperial Roofing and Construction.

## Cause

The order request itself (`portal-action` `queue`, which needs `order_reports`)
succeeds. The portal's project store (`public/portal/scripts/project_viewer.js`,
`Portal.ProjectStore`) then saves the draft project and the ordered project
through the platform projects API (`PUT /v1/platform/organizations/:org/projects/:id`).
That generic document write needs `manage_projects`, which no FirstMeasure
customer role has (manager and custom levels carry `order_reports` and
`view_reports`), and production gives no organization expanded access. The
write is refused with `permission_denied`, and `ProjectStore.save` shows the
server message in its "Project changes not saved" toast.

Read-only production evidence (2026-10-22):

- Web node nginx logs: about 6,400 refused `PUT .../projects/:id` per node per
  day, every one a 129-byte body, which is exactly
  `{"ok":false,"error":"permission_denied","message":"This session does not have permission to perform this action.","details":null}`
  (the expanded-access refusal is 142 bytes). Riedl and Son shows them from
  `projectWindow=` order pages at 18:00–18:19 UTC, right after its orders.
- `POST /v1/platform/portal-action` is not refused for permission (its only
  403s are 95-byte CSRF refusals), so orders are placed.
- The named organizations' users are `manager` or `custom` with
  `order_reports: true` and no `manage_projects`.

Hotfix `c9479381` (1M8-230) gates only core.js's background mirror; it does not
touch `ProjectStore`, so the toast stays after it.

## Fix

Commit `7579af54`: `Portal.ProjectStore.saveRemote`/`removeRemote` keep the
project in the page cache and make no platform call when the organization lacks
expanded access, using core.js's `platformExpandedAccess` (now exported as
`Portal.platformExpandedAccess`). With expanded access the store saves as
before and still reports real failures.

Test: `tests/portal-order-without-expanded-access.test.mjs` (fails on
`c9479381`, passes on `7579af54`); `tests/portal-regressions-20261021.test.mjs`
still passes (21/21 together).
