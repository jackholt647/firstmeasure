# CRM and lead intake audit — 2026-10-15

What is broken, risky or missing in how leads arrive and how the CRM works after
they arrive, judged against the agreed direction:

- a lead is a **contact** with a lead state;
- an **opportunity** is a sales-stage project;
- contacts and opportunities can be **merged**;
- a combined contact + project view is configurable per industry (salon, roofing
  with installs + maintenance plans + repairs, remodeling) through scope sets;
- sales automations run on the same scope / artifact system as production.

This is an index, not a fix list. Nothing in the code was changed.

## How to read this

**Severity**

| Code | Meaning |
|---|---|
| SEC | Security: data reachable or writable without proper authorization |
| BRK | Broken: does not do what it is meant to |
| LOSS | Data-loss or corruption risk |
| GAP | Missing capability |
| SCALE | Works now, will not hold at CRM volume (full scans, unbounded reads) |

**Evidence**

- **Test**: confirmed by a throwaway test run against this checkout on 2026-10-15
  (the test lives outside the repo).
- **Read**: confirmed by reading the code; deterministic unless noted.
- **Read?**: likely from reading, but needs a test before acting on it.

**Rework** says whether the planned contact store / CRM rework would replace it
(**R**) or whether it needs a fix on its own regardless (**F**). **F→R** means fix
now; the rework changes the area later.

Paths are relative to `public/v1/` unless they start with `public/`.

## Detail

### Security

**SEC-1 — internal CRM routes have no authentication.**

`internal/crm/api.ts` registers `/leads/query`, `/leads/export`, `/leads/reassign`,
imports, `/global/:collection` (PUT and DELETE) and `/organizations/:orgId/:collection`.
None of them call `requirePlatformAuth`; only `leadCaller` (api.ts:92) does.

The routes are mounted in `src/app.ts:190`:

- On a single node they are not gated at all.
- On a cluster, the legacy node's gate is the proxy secret (`src/app.ts:106-115`).
  The web node's proxy adds that secret to every `/v1/internal` request
  (`src/app.ts:176-182`), so the gate stops no one.

The test `POST /v1/internal/crm/leads/query` with no cookie returned
`200 {"ok":true,"leads":[]…}`. A rule outside the repo (nginx or similar) may
block `/v1/internal`; that was not checked.

This is FirstMate's own internal sales CRM: Company, Website, Region and
`assigned_to_email` fields, a global `leads.sqlite`, and a PHP sales portal under
`public/measure/sales/`. It is not the customer-facing CRM.

**Resolution (2026-10-19).** The CRM rework removed the lead, import, reassign,
export and generic document routes with the legacy sales portal. What is left of
`internal/crm/api.ts` is the referral routes (partners, rewards, acquisition
campaigns, reports and landing pages). Each now calls `requireReferralStaff`:
a platform session whose email is an active internal user who may manage sales
(a full admin, `manage_users`, `manage_company_settings` or `manage_sales_users`,
which the sales manager role has unless it is turned off). Actor headers and
body fields are not trusted, and writes need the session's CSRF token. Their
only callers are FirstMate staff pages in `public/measure/internal/portal_scripts`
(`acquisition_campaigns.js`, `referral_partners.js`, `referral_rewards.js`),
which now send that token.

One route stays public on purpose: `GET /referrals/logos/:fileName`, because the
referral landing page and the sign-in page show a partner's logo to visitors.
It serves only image files from the logo folder, with `nosniff` and a sandboxing
CSP so an uploaded SVG cannot run script.

The onboarding wizard (`public/libraries/apps/onboarding/wizard.js`) used to
read the whole campaign list from the browser as a fallback for test bonus
links, which exposed every campaign's bonus tokens. The fallback is removed; the
`portal_acquisition_bonus_offer_status` action already resolves a test offer on
the server. Signup itself never used these routes: public lookups go through
`/v1/platform/referrals/public/:code` and `/v1/platform/acquisition/public/*`,
and the published referral actions call `referrals_service` directly.

Tests: `tests/crm-api.test.ts` ("Referral routes refuse anonymous and non-staff
callers…") checks every route refuses an anonymous request (401, even with
spoofed actor headers), a customer owner, an internal user without the
permission, a sales manager with it turned off and an inactive admin (403),
refuses staff writes without CSRF, and accepts an admin, a sales manager and a
user granted `manage_sales_users`. `tests/platform-workflows.test.ts` runs the
acquisition campaign flow through signup with an internal staff session.

### Intake: how leads are created

All callers go through `createPlatformLead` (platform/api.ts:3277).

- **What it reads:** `contacts[]`, or `customer{}` when `contacts` is empty.
- **When it throws:** when address, contacts, title and summary are all empty (3289).
- **What it never writes:** stage, owner or creator.
- **Idempotency:** only when the caller supplies `project_id`.
- **Return value:** `{project, contacts, notification}`.

**INT-1, INT-2, INT-3 — every live chat lead is lost.**

- `chat/service.ts:715-722` and `chat/definition.ts:73-79` pass
  `{name, email, phone, source, notes}` with `as never` hiding the type mismatch.
- The test confirmed this exact shape throws `lead_missing_contact_data`.
- `catch {}` swallows it (service.ts:724, definition.ts:80).
- `leadId = asObject(lead).id` is always `""`: the test confirmed the result has no
  top-level `id`.
- Neither path passes `branch_id`, though one is available.
- If the call shape is fixed as-is, each AI tool call would still create a new
  project, because no deterministic `project_id` is derived from the conversation.

**INT-4 — `stage_id` is ignored.** It is set at `forms/service.ts:682` (and is
configurable at `forms/contracts.ts:177`) and at `canvassing/api.ts:183`.
Nothing reads it. Routing goes only through intake rules.

**INT-5 — canvassing creates duplicates.** `canvassing/api.ts:178-204` does not
check `pin.platform_project_id` or the `lead_created` status. The second
promoted event is deduped (218), so the duplicate project is also missing its event.

**INT-6 — manual `POST /leads` can overwrite projects.**

- `platform/api.ts:2719` passes the parsed body straight through.
- A caller-supplied `project_id` merges into that existing project and resets
  `lead_status`, `contacts` and `created_at`.
- `project_data` is spread last (3321), so it can overwrite any field.
- Auth is only management app access plus CSRF: no `manage_projects` and no branch scope.

**INT-7 — form retries can wipe staff changes.** When the claim is still
`processing` after 2 minutes, the form path calls `createPlatformLead` again over
the existing deterministic project (`forms/service.ts:638-679`). That merge resets
status and contacts. If the work after the write fails, the visitor sees an error
while the project exists (785).

**INT-8 — `projects.lead.create` can duplicate.**
`platform/publication/action-adapters.ts:241` does not use the receipt key as
`project_id`. Which errors map to `failed` (and so allow a retry that creates a
second project) was not checked.

### Intake: email, connections, imports

**IMP-1 — a failed delivery can never be retried.**

- `leads/intake.ts:66-68` marks any `createPlatformLead` error `uncertain`, including
  a failure after the project was written.
- Redelivery returns `duplicate:true, accepted:false` (53-57).
- `reviewLeadDelivery` (77) offers only `imported` or `dismissed`, although the input
  is kept in `input_json`.
- No alert is raised.
- This contradicts `docs/architecture/lead-import.md` ("mapping failures may be
  corrected and redelivered").

**IMP-2 — failures never resolve.** A failure is recorded under the delivery or
event ID (`integrations/lead-intake.ts:28,32,48`); a success is recorded under the
mapped `external_id` (20).

**IMP-3 — email intake gaps.**

- `email/api.ts:638-640` throws without calling `recordLeadRejection`.
- `fromEmail` is computed but not used as a fallback contact.
- `extractLead` runs before the duplicate check, so every redelivery pays for an AI call.
- `fallbackLeadExtraction` returns `is_lead:true` when the AI call fails (476).

**IMP-4 — Google Ads preset.** `integrations/assistant.ts:34` and
`integrations/library.ts:8` omit `externalIdPath`, which then defaults to `"id"`
(`contracts.ts:101`). Separately, `integrations/webhooks.ts:50` rejects numeric event IDs.

**IMP-8 to IMP-12 — contact file import** (`platform/contact_import/api.ts`).

- `contactIdentityKeys` always adds a `name:` key (100-101), and `classifyRows`
  matches on any key (146).
- Commit has no claim (451), and the revision check comes only at the end (544).
- Undo ignores `updated_project_ids` (588-633).
- Phone keys are raw digits (98).
- No `branch_id` is set (284-305).
- `buildExistingContactIndex` lists every project (109).

### Comms matching

`comms/matching.ts`:

- It sorts by `updated_at` (82).
- The archive filter checks `data.status` (65), while archive appears to live in the
  work lifecycle.
- It reads only `phone`, `phone_number` and `mobile` (69).
- It returns null on a storage error without logging (56-59).
- It scans every project for each inbound SMS and email.

`messaging/telnyx_webhooks.ts:172-180` keeps the conversation's project but takes
`contact_id` from the matched project. `comms/calls/service.ts:314-326` searches
every project with no limit, and an empty query returns everyone.

### Contacts

**CON-1 — contacts have no store of their own** (`docs/architecture/contacts.md`;
`contacts/service.ts:22-29`).

- A contact is an object embedded in `projects.data.contacts[]`.
- A standalone contact is a project with `workflow_state:"contact_only"`.
- The same `contact_id` appearing in several projects is a "linked project copy".
- Pickers sort `contact_only` first and keep the first copy per id.

**CON-2 — custom-field writes reach one copy.** `custom_fields/records.ts:284-288`
writes only `target.projectId`'s copy. Values are also split between
`contact_custom_field_values` and per-contact `custom_field_values` (145-146, 286).

**CON-3 — editing a contact can convert a lead project (needs a browser test).**

1. The Contacts app derives `record_project_id` from whichever project first
   contributed the contact (`public/libraries/apps/contacts/app.js:133,246`). That
   project is not necessarily a `contact_only` one.
2. Every lead is a project whose contact has no `contact_only` record. So opening a
   lead's contact and saving targets the lead's project id.
3. `saveContact` (`modal.js:1070-1086`) builds that record with
   `workflow_state:'contact_only'`, `measurement:{}`, `events:[]` and `proposals:[]`
   (because `state.contactRecord` is null, modal.js:1194), then calls `saveRemote`.
4. The linked-project fan-out (1096-1099) then saves the stale copy of the same
   project. That may conflict or revert.

The outcome depends on whether `saveRemote` replaces or patches; it was not run.

**CON-5 — linking changes the primary contact.** `patchProjectContact`
(`modal.js:977-1042`) ignores its `options` (`referenceOnly`). It sets the contact
primary and overwrites `customer_name`, `email`, `phone` and `address` on every
linked project. Merely opening a project from a contact does this too (1128).

**CON-7 — a proposal turns a contact into a deal.** `proposals/storage.ts:462`:
`workflow === "contact_only" ? "proposal_only"`. This is intended and tested
(`tests/proposals-api.test.ts:190`), but it is the opposite of "a contact stays a
contact and gains an opportunity".

**CON-8 — no shared identity rule.**

- `dedupeProjectContacts` (`platform/api.ts:3427-3438`) keys by email, then phone, then id.
- The app's `contactKey` (`app.js:102-111`) groups by email or phone first.
- The server picker keys by id.

So two people who share an email show as one contact, and the save fan-out then
writes one person into the other's projects.

**CON-10 — stale `customers` provider.** The `customers` provider
(`provider-adapters.ts:32`), the chat CRM lookup (`chat/definition.ts:115`) and
search (`api.ts:3912`) read the legacy `customers` collection. No domain code
writes to it.

**STO-1 — contacts are not normalized on Postgres** (reported by the CRM mapping
session, then verified by reading).

- In the file backend, `listDocuments`, `readDocument` and `upsertDocument`
  (`platform/storage.ts:1307, 1318, 1350, 1367`) pass project data through
  `normalizeProjectDataContacts` (659). That function:
  - folds `customer_*` and `primary_contact_*` aliases into `contacts[]`;
  - merges duplicates by id or by name/email/phone;
  - reuses the previous contact ids.
- Each of those functions returns early to `storage_postgres.ts` when
  `isFirstMeasurePostgresEnabled()` is true, and `storage_postgres.ts` never calls
  the normalizer.
- `deploy/digitalocean/firstmeasure-common.env.example:5` sets
  `FIRSTMEASURE_DATABASE_MODE=postgres`.
- Custom-field preparation and validation do run on Postgres
  (`storage_postgres.ts:513-514`); only contact normalization is skipped.

Expected effect in production:

- contact ids, `primary_contact_id`, `contact_ids` and `customer_*` can be missing
  or can change between writes;
- contacts given only as `customer_*` fields never reach `contacts[]`, so pickers,
  matching and the Contacts app don't see them.

Not checked: whether every caller normalizes before writing. Tests that run on the
file backend would not catch this.

**MOD-1 — no enum for project states and types.**

- `workflow_state` values appear as literals across 56 files: `contact_only`,
  `project`, `proposal_only`, `draft`, `document_only`, `measurement_ordered`,
  `measurement_cancelled`, `reorder_prefill`.
- `project_type` means residential, commercial or multifamily in
  `firstmeasure/schemas.ts:97`.
- `createPlatformLead` writes `project_type:"lead"`.
- The Contacts modal writes `project_type:'residential'` on save (`modal.js:1077`).

Lead-ness is therefore spread across `project_type`, `lead_status`, `workflow_state`
and pipeline stage, with no single place defining them.

**Also reported by the CRM mapping session, already indexed:**

- comms matching by full scan, with the most recently updated project winning: MAT-1 and MAT-5;
- the legacy `customers` collection still being read: CON-10.

### Pipeline, stage, call lists, lost

**PIPE-1 — leads can start on a production plan.**

- `scopes/router.ts:177-181` falls back to `sales_pipeline`, then any `pipeline`
  template, then `enabledTemplates[0]`.
- That last one can be a production template, which is started with
  `source_type:"pipeline"` (188).
- `planIsPipelineKind` trusts the template kind (`work/service.ts:727-731`), so the
  plan counts as production.

**PIPE-3 — sold or lost projects can return to a sales board.**
`activePipelinePlans` ignores completed and canceled plans (`router.ts:155`).
Routing re-runs on every project create or update. If a later edit resolves to a
different template, a new pipeline plan starts. The check is not transactional.

**PIPE-5 and LOST-2 — writes that can clobber concurrent edits.**
`scopes/service.ts:347-351` and `work/api.ts:376` write `replace:true` with no
`expected_revision`. Compare `work/service.ts:803-811`, which does it correctly.

**STG-1 — no stage history.** The projection keeps only the current stage
(`work/service.ts:764-790`). The `projects` provider (`provider-adapters.ts:31`)
publishes `status` and `stage` document fields that nothing writes
(`project.stage` was removed per `work/service.ts:733`). `lifecycle` and
`work_projection` are not published.

**CALL-1 — call lists ignore branches.** `crm_call_lists` and
`crm_call_list_entries` have no `branch_id`; uniqueness is
`(organization_id, list_key)` (`internal/crm/call_lists.ts:142-185`).
`callListQueue` returns every list in the organization (411-415).

**CALL-2 — call outcomes go to the wrong database.** `comms/calls/service.ts:251`
updates `crm_call_list_entries` through `withLeadDb` (`internal/crm/leads.ts:398`,
the internal `leads.sqlite`). Call lists live in the `crm-call-lists` store
(`call_lists.ts:14`). Effect:

- the real entry is never completed or removed (including `do_not_call`);
- the wrap-up step throws if the table is absent in `leads.sqlite`.

The older path, `recordCallListDisposition`, uses the right store.

**CALL-3 — "lost" from the New Lead queue does nothing.** The org-rule entry has no
work node, so a `lost` disposition only completes the entry (`call_lists.ts:513-532`).
The newer wrap-up rejects `lost` unless the source nodes are follow-ups
(`comms/calls/service.ts:189-190`). The `contact_lead` node still offers `lost`
(`scopes/presets/index.ts:175`).

**CALL-4 — every queue read rescans.** `syncProjectBackedLists`
(`call_lists.ts:330-406`) loads every project and every open actionable node on each
queue read, plus one query per entry (432).

**LOST-1 — "lost" is final.** `markProjectLost` (`work/followups.ts:143-157`) and
`POST .../lost` cancel the pipeline plans. Nothing reverses this, and "sold" is only
derived from production plans' `sold_at`.

**NOTE-1 and NOTE-2 — new-lead notifications.**

- Push goes to every user in the organization holding `inside_sales` or
  `sales_appointments` (`platform/notifications/delivery.ts:49-53`), whatever their branch.
- Only the in-app list filters by branch (`view.ts:56`).
- With no role holders, nobody is notified and no warning is raised
  (`platform/api.ts:3272-3275, 3348-3385`).

### Consent and contactability

**CNS-1 — form consent never records an SMS opt-in.** The form `consent` block is
only checked as answered (`forms/answers.ts:53-56`); nothing in `forms/` or
`leads/` writes `communication_sms_consents`. With `SMS_REQUIRE_CONSENT=true`
(`src/config/env.ts:328`), texts to a new web lead fail with `sms_consent_required`.
The manual consent route (`messaging/api.ts:1338-1372`) already has the evidence
checks a form would need.

**CNS-2 — contactability gaps.**

- Do-not-call is a phone suppression (`comms/calls/service.ts:212`) that is not
  shared with SMS STOP (`messaging/telnyx_webhooks.ts:43`).
- There is no do-not-email.
- Quiet hours apply only to internal notifications and appointment confirmations,
  not to general or automation SMS.

The working pieces: STOP and START handling, carrier-block opt-out, and per-purpose
consent enforcement.
