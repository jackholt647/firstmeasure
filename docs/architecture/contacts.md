# Contacts, classifications, relationships and media

Contacts retain their existing project/contact-only storage model. A saved reference is `{contact_id, project_id}`: the project identifies the organization-scoped anchor, and the contact ID identifies its embedded contact. Contact-only records take precedence in relationship pickers. Reads do not create anchors, settings, fields or media.

Every saved contact has `contact_kind` (`human` or `org`) and a tags array. The stable built-in `org` tag follows classification and cannot be independently removed or disabled. Its display label uses `contacts.org` in branch terminology. Ordinary tags are IDs from the organization-default `contact_settings` branch module. Only `manage_company_settings` can change the catalog; contact writers select available tags. Renaming a label preserves its ID. Disabling a tag prevents new assignments while existing assignments and legacy string tags survive unrelated edits. File import tags match managed IDs or labels; unavailable tags are reported as skipped.

Default optional contact fields are `relationships.employer` (org contact), `relationships.spouse` (human contact) and `profile_photo` (photo). Administrators can change presentation, order and required constraints while these default paths retain their types and remain available. New custom fields support `contact`, `human_contact`, `org_contact`, `media`, `photo` and `video`, with bounded single/multiple references. Storage validates required values, actual target classification, organization identity, media owner and content type. Scope sets can declare the same types. Existing custom-field publication and field privacy remain in effect.

Contact media uses the existing artifact pipeline with owner type `contact`, owner ID equal to the contact ID, collection `contacts` and `metadata.contact_record_project_id` equal to the anchor. The profile-photo value is a `{media_id}` reference; `profile_media_id` is a derived display alias. The contact Photos & Media tab mounts the shared Feed gallery and reads the central media library rather than writing a separate project photos array. Project navigation and project-only deletion are disabled in that contact gallery. Uploads require `manage_projects`; reads require `view_contacts`. Draft uploads permit required profile photos before a first save, without bypassing membership checks on existing anchors. Profile uploads decode bounded JPEG/PNG/WebP/GIF images.

Photo import is optional and off by default. It accepts embedded vCard bitmap photos or mapped HTTPS URLs. Remote fetches pin a public IPv4 DNS result, reject private networks/credentials, revalidate redirects, and bound size, time and image decoding. A failed photo leaves its successfully imported contact intact and reports a separate row error. Imported media is centrally stored and remains independent of import undo; undo never silently deletes library artifacts.

`contacts.settings` and `contacts.options` are typed data publications. `contacts.settings.save` is an administrator action with durable idempotency receipts. Existing custom-field actions manage field values and reference constraints. HTTP compatibility paths use the same services and storage validation.

Validation: `tests/contact-imports.test.ts`, existing custom-field service/publication/browser tests, `npm run test:publication`, `npm run check`, `scripts/contacts-library-e2e.mjs`, and the Contacts/Feed view-control browser parity checks. The browser fixtures exercise the actual app/gallery/editor code with isolated API fixtures; they do not mutate customer contacts.
